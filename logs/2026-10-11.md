## `merge --resolve` no longer guesses

`--resolve` used to turn any choice other than `delete`/`Copy2` into Copy 1, and
ignored unknown keys, so a typo (`INV-1003=Priya`) silently took Copy 1's value.
Reading `resolveMerge` showed two worse cases: `delete` on a cell conflict silently
took Copy 2's value, and `Copy1` on a delete-vs-edit conflict (where Copy 1 *deleted*
the row) was read by the engine as "keep the edits" — the inverse of "take Copy 1".

- New `bin/resolve-args.ts` (`resolveFromArgs`, `ResolveArgError`) validates every
  `--resolve KEY=CHOICE` and translates it per conflict type. CopyN = "take that
  copy's side", so on delete-vs-edit it means delete if that copy deleted the row,
  keep-with-edits if it edited it.
- Errors (exit code 2, nothing written): unknown/malformed choice, unknown key (lists
  the real ones), duplicate key, `delete` on a CELL/RELATED_EDITS conflict, and
  `--resolve` without `--out` (previously ignored). Choice matching is case- and
  space-insensitive (`copy 1` = `Copy1`).
- `ADD_ADD` conflicts are refused with an explanation: `resolveMerge` plans them but
  ignores the answer (`src/merge/resolve.ts`, "kept minimal"), so accepting one would
  silently write neither row. See the engine gap below.
- Tests (+25, 105 total): `resolve-args.test.ts` (rules and edge cases) and CLI tests
  that run the real binary — exit codes, messages, "nothing written", and a
  delete-vs-edit check on actual output files. 7 of the 9 CLI tests fail against the
  previous CLI.


## ADD_ADD conflicts are now resolved for real (BR-M6, FR-MRG-03)

`planMerge` has always produced an `ADD_ADD` conflict when both copies add the same
key with different content, but `resolveMerge` ignored the answer, so a "resolved"
conflict wrote neither row and the merge screen's choices did nothing.

- **Answers:** `'A'`, `'B'`, or `{ keepBoth: { aKey, bKey } }` (the old key-less `'both'`
  could not work — two rows cannot share a key). New `src/merge/add-add.ts`.
- **Plan** now records Copy 2's anchor, both copies' source rows (so each row's formulas
  re-anchor to where it lands) and the sheet's key column(s) on the conflict.
- **Keep both** gives a row its new key by rewriting its key cell(s): a number key stays a
  number when the new key is numeric; a composite key is the parts joined by " / ".
  Each row is inserted where its own copy put it.
- **Validation (`MERGE_INVALID_RESOLUTION`, new code):** keys must be non-empty, differ from
  each other, and not clash with a row in the Original (`baseRowKeys`, new, in impact.ts), a
  row another proposal adds, or another kept row. `resolveMerge` now also checks every answer
  fits its conflict type (`assertChoiceFits`), closing the silent-fallthrough class — e.g.
  `'delete'` on a CELL conflict used to take Copy 2's value. Behaviour change for direct
  library callers; the merge screen and CLI only ever sent valid answers.
- **Merge Log** records the kept row(s), their source, and "was KEY in <copy>" when renamed.
- **CLI:** `--resolve KEY=Copy1|Copy2` keep that copy's row; `KEY=both:NEWKEY` keeps both
  (Copy 2's row under NEWKEY). An answer the engine rejects exits 2 like other usage errors.
  Previously ADD_ADD was refused outright.
- **Verified** end to end on a generated workbook (INV-4 added by both copies): all three
  answers go through plan -> resolve -> impact preview -> patch -> re-read; totals extend
  over both kept rows; each row's formula lands on its own Excel row; and LibreOffice
  recalculates the patched files to the expected totals (1,100 / 1,300 / 1,800).
- **Tests** (+38 in this change; 143 total): `merge-add-add.test.ts` (25) plus parser and
  CLI cases.

Found, not changed: the reader (`readWorkbook`) drops a formula cell that has no cached
value (SheetJS skips it unless `sheetStubs` is on). Patched merge output has no cached
values by design (Excel recalculates on open), so re-reading it loses those formulas -
e.g. comparing a merged file against its Original would see the formulas as gone. Files
written by openpyxl or similar behave the same way.

## Reader: formulas saved without a cached value are no longer dropped

SheetJS discards a formula cell that has no `<v>` unless `sheetStubs` is on, so the reader
saw openpyxl-style files — and SheetLens's own merge output — with every formula missing.
Re-opening a merged file made all of its formulas vanish (and a compare against the Original
would have buried the real edits in noise).

- **Cause confirmed** with hand-built worksheets: no `<v>`, empty `<v/>` and shared-formula
  children are all absent without stubs; with stubs they arrive as `t:'z'` + `f` (the adapter
  already handled that shape) and shared formulas are expanded.
- **Not global:** `sheetStubs` also materialises styled blank cells (measured on 1.6 M of them:
  ~2x read time, ~3x heap). New `src/read/formula-scan.ts` finds a formula-only cell by
  scanning each worksheet (one at a time, 8 MB windows, early exit); the reader enables stubs
  only then. Overhead for files that do not need it: ~10 % of read time on a deliberately
  heavy 100k-row file. A `t="str"` formula returning "" is correctly not flagged.
- **Message fix:** a changed formula whose other side has no saved value used to print
  "₹29 → (blank)". It now shows the formula and says Excel will calculate the value.
- **Tests (+19, 162 total):** every cell shape, scanner precision (Excel fixtures never
  trigger it), a cell straddling the window boundary, and an end-to-end re-read of a merged
  file: the 6 Summary formulas survive, the 84 formula cells with no saved value are
  "recalculated", exactly the 4 widened totals are `formula_changed`, none is overwritten.
  Mutation-checked: with stubs forced off, 3 of the 4 re-read checks fail (0 of 6 Summary
  formulas survive); with no window overlap the boundary test fails.

Noticed, not changed: comparing a merged file with its Original raises a High CHK-03 for the
removed row because its key appears in the new "SheetLens Merge Log" sheet's text. That is
the check scanning the log sheet the merge itself added.

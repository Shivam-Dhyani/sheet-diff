## `merge --resolve` no longer guesses

`--resolve` used to turn any choice other than `delete`/`Copy2` into Copy 1, and
ignored unknown keys, so a typo (`INV-1003=Priya`) silently took Copy 1's value.
Reading `resolveMerge` showed two worse cases: `delete` on a cell conflict silently
took Copy 2's value, and `Copy1` on a delete-vs-edit conflict (where Copy 1 *deleted*
the row) was read by the engine as "keep the edits" — the inverse of "take Copy 1".

- New `bin/resolve-args.ts` (`resolveFromArgs`, `ResolveArgError`) validates every
  `--resolve KEY=CHOICE` and translates it per conflict type. CopyN = "take that
  copy's side", so on delete-vs-edit it means delete if that copy deleted the row,
  keep-with-edits if it edited it.
- Errors (exit code 2, nothing written): unknown/malformed choice, unknown key (lists
  the real ones), duplicate key, `delete` on a CELL/RELATED_EDITS conflict, and
  `--resolve` without `--out` (previously ignored). Choice matching is case- and
  space-insensitive (`copy 1` = `Copy1`).
- `ADD_ADD` conflicts are refused with an explanation: `resolveMerge` plans them but
  ignores the answer (`src/merge/resolve.ts`, "kept minimal"), so accepting one would
  silently write neither row. See the engine gap below.
- Tests (+25, 105 total): `resolve-args.test.ts` (rules and edge cases) and CLI tests
  that run the real binary — exit codes, messages, "nothing written", and a
  delete-vs-edit check on actual output files. 7 of the 9 CLI tests fail against the
  previous CLI.

Open engine gap (not changed here): `resolveMerge` does not apply `ADD_ADD`
resolutions, and does not validate that a choice fits the conflict type. The
SheetLens merge UI only offers valid choices per type, but it does offer ADD_ADD
choices that currently have no effect on the output.
